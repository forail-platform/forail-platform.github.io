Forail 2026.11.0 — Release Notes

Release date: 2026-11-20 Based on: Forail 2026.07.1 License: Apache License 2.0

Overview

2026.11.0 ships two things at once: the new monitored servers feature for the Forail Mobile companion, and the whole "make-it-true" body of work that had been staged as 2026.10.0 but was never tagged or published. Several features Forail advertised did not work in the published images — event-driven automation, drift detection, outbound webhooks and WebAuthn — and the configuration objects behind them could be rewritten by any member of an organization. This release fixes that, puts the whole Django test suite (about 2,300 tests) into CI on every pull request, and adds a backup and restore that actually restore.

Supersedes the unreleased 2026.10.0. No 2026.10.0 images were ever published; everything that was planned for it is in 2026.11.0.

Backend, frontend and the Helm chart move together to 2026.11.0.

New — monitored servers

A user registers their own server running forail-agent and watches it from Forail Mobile and the web UI, at /api/v2/monitored_servers/.

  • Ownership and access. The owner, the admins of the server's organization and superusers manage it; only the organization's admins and superusers grant or revoke read access. Anyone else gets 404 — a server they cannot see does not exist to them.
  • No long-lived secrets in the UI. Enrolment uses a one-time code with a ten-minute countdown and the exact forail-agent enroll command to copy; token rotation and the enrolment codes go through the Forail Mobile service API, and an agent token is never shown.
  • Frontend. A Resources → Monitored servers list with online state, organization, owner and last report; an Install panel that issues the one-time code; and an Access tab where admins grant and revoke while everyone else sees who has access, read-only.
  • Quota and migration. A per-user quota (MONITORED_SERVERS_PER_USER, default 10), and import_monitored_servers brings servers registered in Forail Mobile before this under platform RBAC.

Security

Upgrade if you use any of: event rules, outbound webhooks, drift alert rules, policies, scanners, or the service catalog.

  • Organization members could rewrite configuration they should only read. The API for event rules, outbound webhooks, drift alert rules, policies, scanners and catalog items checked only that the user was logged in and in the organization. A plain member could disable a policy, point an outbound webhook at their own URL, retarget an event rule to launch a job template in another organization, read or rotate an event rule's inbound webhook key, and trigger a test send of any outbound webhook by id. These objects now follow the AWX rule for notification templates: the organization reads, its admins change. An event rule's author must be able to start every template its actions launch; a catalog item's publisher must be able to execute its template.
  • Secrets in the activity stream. An outbound webhook's HMAC key and custom headers, a WebAuthn credential's key material and a service request's survey answers were recorded in the activity stream, which auditors can read and which is shipped to external loggers. They are now excluded.
  • Outbound webhooks are scoped to their organization. (They were not sent at all before this release — see below — but the dispatch matched webhooks across organizations.)
  • Branding favicon URL validation (frontend). The favicon in the unauthenticated host-keyed branding response is applied only when it is an http(s) or same-origin relative URL, blocking javascript:/data: schemes.

Fixed — features that did not work

  • Event-driven automation never fired. The rule engine imported celery, which Forail does not ship; the public receiver raised on every event. Now verified end to end: a signed webhook launches the job, with the payload in its extra vars.
  • Drift detection never recorded anything. The capture that runs after every fact-caching job failed on the same import. Snapshots and drift detections are now recorded; old snapshots are cleaned up every six hours.
  • Outbound webhooks were never sent on job events — nothing called them — and the sender imported httpx, which Forail does not ship. They now fire on job and workflow start, success, failure and cancel, signed with X-Forail-Signature.
  • WebAuthn passkeys could not be registered. The webauthn library was missing from the image.
  • Only superusers could create policies, scanners, event rules, webhooks, drift rules and catalog items; everyone else got a 500. Deleting any of them failed for everybody.
  • Saving any of eight Forail objects failed while the activity stream was on (the default).
  • Editing a policy failed while the OPA sidecar was unreachable.
  • After an SSO login users landed on a blank page; the browsable API's logo was missing; any non-API URL that reached the backend directly returned 500.

Backup, restore and upgrade

The documented backup command did not run, and restore.sh replaced nothing, reported success, and moved the database sequences backwards so new records failed afterwards. Both are rewritten:

  • backup.sh writes a compressed custom-format dump plus a .meta file that records the Forail version and a fingerprint of FORAIL_SECRET_KEY.
  • restore.sh refuses while the stack is writing, refuses a backup taken with a different secret key, restores into a new database and swaps it in — so a failed restore changes nothing and the previous database is kept until you drop it.
  • scripts/test-backup-restore.sh checks the round trip on a running stack.

Commands are in the Administrator Handbook.

AWX migration

import_from_awx gains --report-file (a JSON plan of every object it would create or update, for review with --dry-run), prints every warning grouped by what you must do about it, reads secrets from --token-file / --password-file, and no longer erases credential-type injectors an admin re-approved when it is run again. See AWX → Forail Migration.

Removed

  • The never-built legacy AWX React UI (about 16 MB of every backend image).

Upgrading

Take a backup with the new backup.sh, keep .env, set FORAIL_TAG=2026.11.0, docker compose pull && docker compose up -d. On Kubernetes, point the Helm chart at 2026.11.0 (the chart pins the matching backend and frontend images) and helm upgrade. forail-init applies the new migrations.

Verified for this release: an in-place upgrade from 2026.07.1 to 2026.11.0 on a three-control-plane k3s cluster — rolling update, migrations applied, existing data preserved, and a create/read/delete round trip through the API after.

Breaking for API clients that relied on the old behaviour: a request for one of the configuration objects above in another organization now answers 403 instead of 404, and organization members can no longer change them.

Known issues

  • Third-party license texts (licenses/) are still missing from the backend repository.
  • Some Forail models differ from their migrations in index names and field options; no data is affected.
  • See What Forail changed relative to AWX for the full picture.
